Trustworthy Agentic Apps Need Device-First Architecture

A walkthrough of the ScrolLess architecture: the agent fetches, the relay stays blind and the device owns the data.

This is a three-part series on agentic content apps. Reading order: Part 1: Personal Agents Make Experience More Important Than Content Acquisition → Part 2: The Hard Part of Letting Agents Gather Content → Part 3: Trustworthy Agentic Apps Need Device-First Architecture (you are here)

The Architecture Has to Earn the Trust

Part 1 set out the core inversion: personal agents handle integrations, apps focus on presentation and data lives on the device. Part 2 looked at the friction that still stands in the way: platform access, two distinct trust problems, reliability and product design.

Saying "your data stays on your device" only carries weight if the system enforces it. A relay server that promises not to log your feed is very different from one that only ever receives ciphertext. Even if incentives change later, there's nothing readable on the server to inspect.

What follows is a walkthrough of the design I'm building in ScrolLess. The core pipeline is running, though the app itself is still in active development. I'm writing it down because the architectural choices are the part I actually wanted to test.

Five Principles Before the Diagram

Without explicit constraints, it's easy to add one reasonable server-side shortcut at a time until you've quietly rebuilt a normal cloud app. Five principles keep this design honest:

User-owned data by default. Feed items, read state, preferences and saved content live on the device. The app reads straight from on-device storage, with nothing held centrally as a condition of using it.

Agents handle integrations. The app has no OAuth flows, API clients or rate-limit logic, and no knowledge of how YouTube or X work under the hood. That complexity stays in the agent layer, which runs under the user's control.

Apps compete on experience. When data isn't locked inside a backend, switching apps becomes practical. As others looking at agentic interface design have noted, that pushes apps to compete on curation and usability instead of integration count.

Cloud stays optional. Multi-device sync, reliable background scheduling and heavier features like cross-source summarisation can live in an optional cloud layer, while the core single-device experience works completely without it.

Clear trust boundaries. It should be straightforward to explain what runs on the device, what leaves it and what any server in the middle can see. If the relay can read the feed, the model has already failed.

The Full Flow

With those constraints in place, the delivery path stays simple. A scheduled task triggers my personal agent. The agent loads its workflow from an MCP server, collects new items from configured sources, normalises and deduplicates them, encrypts the payload with the device's public key and submits it. A blind relay forwards that ciphertext to the device, which decrypts it into IndexedDB so the app can render locally with no network round-trip.

Two choices do most of the heavy lifting here. Encrypting at the agent keeps the decryption key off every server in the chain, so the relay routes payloads it can't inspect. And making the device the terminal store means normal reading never waits on a cloud database.

Deterministic Workflows and MCP's Two Roles

Anyone who has run agents on a schedule knows where loose prompts break down. Tell an agent to "fetch my YouTube subscriptions and add them to my feed" and it might work three times, then invent a field name or skip a source on the fourth. For a background task handling real data, reliability comes from constraining the workflow, not hoping the model improvises well every time.

It's the same lesson I came back to in Agents Get Better by Becoming More Human: making agents dependable usually means giving them explicit steps, typed boundaries and predictable checks.

In ScrolLess, MCP (Model Context Protocol), now stewarded by the Agentic AI Foundation, handles two separate jobs that are worth keeping distinct.

First, MCP acts as an instruction layer. The server exposes named workflows such as sync_feed alongside typed tools, schema definitions, source-specific skill documents and current preferences. The agent doesn't need ScrolLess internals baked into its prompt; it fetches the instructions it needs at runtime. As others exploring MCP have pointed out, separating general agent capability from app-specific knowledge is one of the protocol's cleanest properties.

Second, MCP acts as an ingestion interface. Once the agent has gathered and encrypted content, it submits a validated tool call back to the MCP server instead of writing straight to a backend endpoint. That gives the system one typed, auditable checkpoint where external data enters.

Walking Through sync_feed

The easiest way to see how the pieces fit is to trace a single run of sync_feed, the scheduled workflow that populates my feed.

The agent starts by calling get_feed_state. One call returns everything it needs before touching an external site: the timestamp of the last successful sync, the enabled sources with their priorities, any skip rules and the device's public key for encryption.

Next, it loads the skill files for each enabled source from the MCP server, such as skills/youtube.md and skills/x.md. Each skill is a concrete guide tested for that platform: where to navigate, which elements to extract, what to ignore and how to handle edge cases like deleted posts or private accounts.

Working through each source, the agent collects items published since the last sync, deduplicates them against known url_hash values and ranks them using my priority rules. The output is a flat list matching the app's schema, regardless of where each item originated.

Before anything leaves the agent, the payload is encrypted with the device's public key (ECIES P-256 + AES-256-GCM). The agent then calls write_feed_items with the ciphertext, the ephemeral key needed for decryption and minimal source metadata. MCP validates the call and passes it to the relay; the relay pushes it to the device; the device decrypts, deduplicates against existing IndexedDB records and updates the feed on next render.

If the device is offline, the relay queues the encrypted payload until it reconnects. The sync window only advances once the device acknowledges delivery, so a queued batch can't quietly skip past items I haven't received yet.

Where the Data Lives

The device

Feed items, read state, preferences, saved items and sync logs all sit in IndexedDB. Reading works offline and feels immediate because nothing waits on a remote query. Deleting local app data actually deletes everything. Deduplication (by url_hash) and retention cleanup (against each item's fetched_at timestamp) also run client-side.

The relay

The relay only exists because a scheduled agent and a phone aren't always online at the same time. It queues and forwards ciphertext, drops it once delivered and holds no record of the content inside.

The coordination backend

A small server handles the plumbing the relay can't: Web Push subscriptions, device registration, source configuration metadata and MCP server discovery. Its job is coordination, not holding feed content.

Keeping Cloud Optional

There are real conveniences a cloud layer can add later: multi-device sync, longer offline queuing, hosted scheduling or cross-source summarisation. In my design, those stay strictly additive. Someone running their own agent on a single device should get a complete app without opting into cloud sync, and opting in shouldn't change what the server can read.

Where ScrolLess Is Today

ScrolLess puts these pieces together as a Preact PWA backed by IndexedDB, with an external agent collecting from my logged-in browser sessions (currently YouTube subscriptions and the X following timeline). The app itself has no direct connection to either platform.

The core pipeline is working end to end: MCP-guided collection, encryption at the agent, blind relay delivery and on-device decryption and storage. What's still being built out is a broader set of source skills, the preferences and source-management UI and optional sync.

Building the trust boundary into the first commit is slower than starting with a central database and promising to clean it up later. For an app meant to sit across personal feeds, that trade-off felt worth making from the start.

Agents gather, devices hold the data and apps earn their place on the experience. The architecture is what turns that from a promise into something you can actually trust.
